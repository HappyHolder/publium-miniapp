# Collaber: план реализации функции Community Manager

Дата: 21 сентября 2026 года.

Статус на 27.09.2026, после обновления группового сценария: функция развёрнута; только в Test Publium Chat включён автоматический подбор по новым интро с разрешением автора прямо в группе. Периодические предложения выключены, лимит — одна инициатива за 24 часа. Загрузка архива убрана из обычного интерфейса; база новых сообществ формируется постепенно из интро, служебный разовый импорт сохранён. Вкладки «Участники» и «Подборы» поясняют базу, историю и черновики; пустые результаты не показывают обложку и оценку. Пройдены 138 серверных тестов, сборки, security/frontend smoke и интеграция с отдельной PostgreSQL. Живое совпадение и знакомство двух участников ещё не подтверждены: в тестовой базе пока один профиль. Подробности текущего выпуска — в [отчёте группового пилота](collaber-group-pilot-2026-09-27.md), первоначального — в [отчёте реализации](collaber-release-2026-09-21.md). Ниже сохранён исходный план; более позднее решение об архиве заменяет первоначальный план публичной загрузки истории.

## 1. Что должно получиться

Collaber — подключаемая функция существующего Community Manager. Она помогает участникам сообщества находить людей для совместных проектов, обмена опытом, продвижения и других профессиональных задач.

Для участника всё выглядит просто: он обращается к привычному боту сообщества, описывает свою задачу и получает до трёх подходящих людей с объяснением, чем они могут быть полезны друг другу. Новые интро автоматически пополняют базу. Если появляется хорошая возможность для знакомства, CM может предложить её сам в рамках настроек владельца.

Первый пилот — Collaborations. Основа подбора универсальная; сфера сообщества и цели знакомства задаются настройками. На первом этапе реализуем профессиональные коллаборации. Другие сценарии, включая личные знакомства, требуют отдельных правил и добровольно заданных предпочтений и в первый запуск не входят.

У Collaber общие с CM личность, исполнитель, контекст сообщества, журнал и ограничения отправки. Название функции в настройках — **«Collaber · Поиск партнёров»**. Имя самого бота сохраняется тем, которое выбрал владелец.

## 2. На какую существующую основу опираемся

Проверено по локальному коду на дату документа:

| Область | Уже есть | Что добавляем |
| --- | --- | --- |
| Управление CM | `CommunityManagerPanel.tsx`, черновик и применение настроек, пауза | Раздел «Функции» и настройки Collaber с той же логикой применения |
| Память участников | `CommunityManagerParticipant`, идентификация по менеджеру и Telegram ID | Проекты, предложения, потребности, актуальность и предпочтения участия |
| Подтверждения фактов | `CommunityManagerParticipantClaim` и `ClaimEvidence` | Источники из импорта, срок актуальности, исправления и происхождение данных |
| Поиск экспертов | `relevantExpert()` в `participantMemory.ts` | Полноценный поиск партнёров с несколькими критериями и историей рекомендаций |
| Единый агент | `agentRuntime.ts`, инструменты чтения памяти и контекста | Инструмент подбора, типизированный результат и проверка источников |
| Активности | Планировщик, директор активностей, доставка | Поводы для коллабораций в общем механизме принятия решений |
| UI | `GlassCard`, `Button`, `Switch`, `NumberStepper`, справочные панели | Экраны и состояния нового модуля из тех же компонентов |
| Эксплуатация | Express, Prisma, PostgreSQL, Docker Compose | Дополнительные таблицы, фоновые задания и диагностические показатели |

Текущий `relevantExpert()` выбирает среди 20 недавних подтверждённых экспертов по совпадениям слов. Его нельзя считать готовым мэтчингом или переносить его ограничения в новую функцию: подходящим партнёром может быть обычный участник с хорошим интро.

Разговорные сообщения имеют срок хранения и очищаются. Доказательная память уже отделена от них, однако импорт и долгосрочная актуальность профилей потребуют явной политики хранения источников.

Документы-ориентиры: `community-manager-roadmap.md`, `community-manager-agent-runtime.md`, `community-manager-activity-engine.md`, `community-manager-human-architecture-draft.md`. Если ранняя концепция расходится с текущей реализацией, проверяем код и фиксируем итоговое решение в документации.

## 4. Единый стиль интерфейса — обязательные условия

Источники оформления: `src/styles/globals.css`, `src/components/ui/`, `src/components/community-manager/`.

| Элемент | Решение для Collaber |
| --- | --- |
| Фон | Существующий `--bg: #070708` |
| Карточки | `GlassCard`, поверхности проекта, скругление основных карточек 18 px |
| Основной акцент | Существующий оранжевый `#FF6A00`, через общие стили и компоненты |
| Текст | Текущий системный шрифт проекта, белый основной и серый дополнительный текст |
| Границы | Существующие полупрозрачные светлые границы |
| Иконки | `lucide-react`, сопоставимые размеры и толщина линий |
| Управление | Общие кнопки, переключатели, поля и панели справки |
| Компоновка | Существующий мобильный контейнер до 430 px, вертикальные карточки, привычные отступы |
| Сохранение | «Сохранить» сохраняет черновик, «Применить» активирует настройки |

Дополнительные требования:

- Основной текст интро и объяснений читаемый, ориентир 14–16 px; мелкие подписи не несут единственный важный смысл.
- Основные элементы управления имеют область нажатия не менее 44 × 44 px. При необходимости расширяем область через `className`, сохраняя общий компонент.
- Проверяем контраст текста, включая кнопки с оранжевым фоном. Доступность исправляем согласованно с общим компонентом, не вводя отдельную палитру Collaber.
- Статус выражается текстом и при необходимости иконкой, а не только цветом.
- У полей есть подписи, у кнопок с иконками — доступные названия; виден фокус, панели корректно возвращают его после закрытия.
- Длинные имена, интро, проекты и ссылки не ломают ширину. Длинное описание раскрывается внутри карточки или панели.
- Нижние действия не перекрывают содержимое, клавиатуру и safe area Telegram.
- Анимации короткие и необязательные; учитывается `prefers-reduced-motion`.
- Учитываем состояния: первый вход, нет участников, импорт идёт, импорт завершён частично, ошибка, нет подходящих людей, функция на паузе, настройки ещё не применены.
- Проверяем 320, 375, 390 и 430 px, а также широкий экран с сохранением текущего ограничения контейнера.
- Перед приёмкой сравниваем снимки существующих экранов CM и Collaber рядом. Новая функция должна восприниматься частью того же приложения.

## 5. Пользовательские сценарии и экраны

### 5.1. Владелец подключает функцию

Путь: **Сообщество → Community Manager → Функции → Collaber**.

Карточка функции содержит название, краткое описание «Находит участников для совместных проектов», статус и действие «Настроить». Неактивная функция не запускает импорт, подбор или публикации сама.

Первичная настройка состоит из четырёх шагов:

1. **Цель.** Тип сообщества и задачи: партнёрства, обмен аудиторией, поиск специалиста, обмен опытом. Для Collaborations — владельцы проектов и мини-приложений, разработчики и маркетологи. Несколько целей можно включить вместе.
2. **Участники.** Загрузить историю, увидеть предварительный разбор и запустить импорт; либо начать собирать новые интро без архива.
3. **Подбор.** Определить важные критерии: что человек ищет, чем может помочь, тематика, аудитория, язык, формат сотрудничества. Дополнительные параметры раскрываются по необходимости.
4. **Поведение.** Ответы по запросу, предложения после новых интро, периодические подборки; кому показывать предложения и какие ограничения действуют.

В конце показываем понятное резюме будущей работы, состояние данных и кнопку применения. Импорт — отдельная явная операция с данными; сохранение формы не запускает импорт автоматически. Пользователь видит, какие действия уже выполнены, а какие остались в черновике.

### 5.2. Владелец управляет функцией

Внутри Collaber три вкладки:

| Вкладка | Содержимое и действия |
| --- | --- |
| Участники | Поиск, фильтры «Есть интро», «Нужно уточнить», «Готов к сотрудничеству»; открыть профиль, исправить данные, посмотреть источник, управлять импортом |
| Предложения | Черновики, предложенные знакомства, отклики и завершённые знакомства; просмотреть причины подбора, отправить разрешённое предложение, отклонить с причиной |
| Настройки | Цель сообщества, правила подбора, режимы инициативы, ограничения, пауза функции |

Данные участников общие с разделом «Участники и связи». Для него сохраняем существующий вход и добавляем переход к расширенному профилю. Два экрана используют одну сущность и одинаковые изменения, а не две независимые базы.

Карточка участника показывает: имя, доступный контакт, проект, чем полезен, что ищет, дату актуальности, источник и готовность получать предложения. Административные заметки и внутренние оценки CM в публичную карточку не попадают.

### 5.3. Участник ищет людей

Пример запроса: «Найди партнёров для кросс-промо моего мини-приложения».

CM использует интро автора и текущий запрос. Если не хватает существенной информации, задаёт один короткий уточняющий вопрос. Повторно спрашивать уже известное не нужно. Сам запрос используется сразу; делать из него постоянный интерес человека без подходящих оснований не следует.

Ответ содержит до трёх рекомендаций. Для каждой: кто этот человек, чем занимается, почему подходит под конкретную задачу, возможный первый шаг и источник данных. Если потребность описана давно, это явно отмечается или кандидат не допускается к автоматическому предложению.

Пример вымышленного ответа для проверки сценария:

> Анна развивает мини-приложение для изучения языков и в интро указала, что ищет партнёров для обмена аудиторией. Если ваша аудитория тоже изучает языки, можно обсудить совместный челлендж. Размер аудитории в профиле не указан — его стоит уточнить.

Основное действие при доступном публичном контакте — «Написать [имя]». Дополнительные действия: «Посмотреть интро», «Уточнить подбор», «Не подходит». Для знакомства через посредничество CM предусмотрена кнопка «Помочь познакомиться». При отсутствии надёжных совпадений CM честно объясняет, каких данных не хватает, и не заполняет ответ случайными людьми.

### 5.4. Участник управляет своим участием

Нужны простые действия «Мой профиль», «Исправить», «Не предлагать меня», «Не упоминать меня», «Удалить данные Collaber». Реализуем через доступный диалог с ботом и, где уместно, компактный экран Mini App.

Различаем разрешение показывать профиль в поиске, разрешение публично упоминать и согласие на конкретное знакомство. Существующий `mentionEnabled=true` не считается согласием на все новые действия Collaber.

### 5.5. Три способа получить подбор

Участнику не обязательно каждый раз писать боту отдельную просьбу. Предусмотрены три входа:

| Сценарий | Действие участника | Действие CM |
| --- | --- | --- |
| Запрос в группе | Обращается к текущему боту: «Найди партнёров для кросс-промо» | Использует профиль и запрос, при необходимости уточняет задачу, отвечает в той же ветке |
| Новое интро | Представляется в чате обычным сообщением | Обновляет профиль; при полезном совпадении и разрешённой инициативе предлагает конкретного человека |
| Кнопка в приветствии или закреплённом сообщении | Нажимает «Найти партнёра» | Открывает личный сценарий у выбранного CM-бота с сохранённым контекстом сообщества |

Пример инициативного ответа после интро, имена вымышлены:

> Алексей, ты написал, что ищешь мини-приложения для совместных запусков. Мария недавно искала маркетолога для своего проекта. Возможно, вам стоит обсудить сотрудничество.
>
> [Написать Марии] [Посмотреть её интро]

Новое интро не обязывает CM публиковать ответ. Сначала проверяются совпадение, актуальность запроса, допустимость показа и ограничения инициативы. В пилоте такие предложения сначала проходят через черновики владельца.

Пример текста для приветствия или закреплённого сообщения:

> В этом сообществе можно найти людей для совместных проектов. Расскажи, кого ищешь, — помогу подобрать участников.
>
> [Найти партнёра]

Кнопка ведёт к исполнителю Community Manager, даже если само приветствие отправил Moderator. Участник при необходимости нажимает «Начать», после чего CM спрашивает: «Для какой задачи ищешь человека?». Наличие открытого личного диалога не заменяет проверку доступа к сообществу. В личном сценарии задача и рекомендации не публикуются автоматически в группе.

Владелец добавляет кнопку в приветствие или размещает подготовленное сообщение для закрепления. При подключении функции не перезаписываем существующий текст и кнопки приветствия. Текущий редактор допускает до трёх кнопок: если все места заняты, предлагаем владельцу выбрать замену либо использовать отдельное сообщение.

### 5.6. Как выглядит сообщение с рекомендациями

Основной формат первого релиза: **одно сообщение с необязательной картинкой, 1–3 рекомендациями и кнопками**. Для каждой рекомендации указываем человека, проект, основание совпадения и возможный первый шаг. Количество фактов ограничиваем так, чтобы сообщение удобно читалось на телефоне; полное интро доступно отдельно.

Пример структуры, все люди и сведения вымышлены:

```text
[Обложка сообщества: «Партнёры для тебя»]

Нашёл два подходящих варианта.

Анна · приложение для языков
В интро указала, что открыта к обмену аудиторией.
Вам можно обсудить совместный языковой челлендж.

Максим · сообщество студентов
Ищет полезные продукты для своей аудитории.
Можно предложить участникам попробовать твоё приложение.

[Написать Анне] [Написать Максиму]
[Посмотреть интро]
[Уточнить подбор]
```

Это схема содержимого, а не обещание точного расположения элементов во всех клиентах Telegram. При длинных подписях кнопки располагаем по одной в строке. Если кандидатов несколько, «Посмотреть интро» сначала предлагает выбрать человека; когда кандидат один, открывает его источник сразу.

В группе ответ на запрос виден участникам группы. Поэтому в нём только разрешённые для этой аудитории сведения. Уточнения и персональная обратная связь относятся к автору запроса: нажатие другим человеком не меняет чужой подбор; ему предлагается начать собственный. Общедоступные кнопки контакта могут открывать профиль, но не принимают приглашение от имени автора.

### 5.7. Что происходит при нажатии «Написать»

Если у кандидата есть проверенный публичный username и показ контакта разрешён, кнопка открывает диалог с ним. Можно подставить заготовку первого сообщения:

> Привет! Collaber предложил познакомиться. Хочу обсудить кросс-промо наших проектов.

Участник редактирует и отправляет текст сам. Переход по кнопке не отправляет сообщение автоматически и не означает, что общение состоялось. Обычная URL-кнопка не сообщает боту о факте переписки; результат узнаём только из добровольного отзыва, не выдаём переходы за состоявшиеся знакомства.

Такой сценарий поддерживается [ссылками Telegram с username и черновиком текста](https://core.telegram.org/api/links#public-username-links). Для действий и ссылок используется [клавиатура сообщения Telegram](https://core.telegram.org/bots/api#inlinekeyboardbutton).

Если надёжного доступного контакта нет, не придумываем ссылку из имени и не гарантируем переход по одному Telegram ID. Предлагаем «Помочь познакомиться», если доступен разрешённый канал приглашения, либо объясняем, что контакт нужно уточнить. Посредничество CM с приглашением второй стороны — отдельный сценарий этапа 7; оно не является обязательным дополнительным шагом перед самостоятельным обращением к разрешённому публичному контакту.

### 5.8. Картинка и оформление сообщения

В первой версии владелец загружает общую обложку Collaber для своего сообщества. Используем знакомый сценарий приветствий Moderator: загрузить изображение, увидеть предпросмотр, заменить или убрать его. Сохраняем обложку в настройках функции и повторно используем для подборов.

- Картинка необязательна. Можно выключить её для обычных ответов, оставив для отдельных подборок.
- Имена, причины подбора и контакты остаются обычным текстом сообщения, а не только надписями на картинке.
- Предпросмотр показывает изображение, пример текста и кнопки вместе. Примерные данные явно обозначены и не отправляются в рабочий чат.
- При ошибке загрузки или отправки изображения допускается текстовый вариант через общий механизм доставки, если подтверждено, что исходное сообщение не отправлено. Неопределённый исход не запускает слепую повторную отправку.
- Автоматическая карточка с названиями проектов и их разрешёнными логотипами — последующее улучшение; для первого релиза достаточно загруженной обложки. Генерация новой AI-картинки на каждый запрос не требуется.
- Экраны управления и оформление изображения соответствуют стилю проекта. Вид самого сообщения и стандартных кнопок определяется Telegram и темой пользователя; CSS Mini App не переносится в чат.

Проверенная основа в проекте: `ModeratorRichWelcomeEditor.tsx` управляет изображением, текстом и кнопками; `sendWelcome()` в `server/src/routes/moderator.ts` собирает изображение и текст и отправляет их через `sendRichMessage` с клавиатурой. Переиспользуем общие компоненты и механизм отправки, сохраняя для Collaber исполнителя, права, журнал и лимиты CM. Дополняем клавиатуру динамическими контактами и действиями; готовая логика приветствия сама по себе ещё не реализует подбор.

Приоритет первого запуска: **запрос или «Найти партнёра» → одно сообщение с обложкой и 1–3 рекомендациями → «Написать» конкретному человеку**. Инициативные знакомства включаются после проверки качества.

## 6. Последовательность выполнения

### Этап 0. Проверить исходный файл и зафиксировать пилот

**Действия:**

- Получить файл истории: сейчас известен только факт его наличия, формат и содержимое не изучены.
- Проверить формат, кодировку, размер, диапазон дат, количество чатов, сообщения с интро, наличие ID авторов и сообщений, правок, ответов и пересылок.
- Выбрать адаптер под фактический формат. Сначала поддержать используемый файл, затем добавлять другие форматы по необходимости.
- Определить, как однозначно связать импортируемый чат с сообществом Collaborations. Импорт истории сам по себе не доказывает, что человек всё ещё состоит в группе.
- Выделить небольшую выборку интро, обычных сообщений и неоднозначных случаев для ручной проверки качества.
- Зафиксировать типы коллабораций для пилота, разрешённую видимость профилей, срок хранения и правила инициативы. Предлагаемый старт: поиск по запросу и черновики инициатив для владельца.
- Проверить текущий приём сообщений выбранным CM-ботом и его настройки доступа к сообщениям.

**Результат:** описание формата, карта полей, примеры ожидаемых профилей, набор контрольных задач и параметры пилота.

**Готовность:** на выборке понятно, кто автор интро и к какому сообществу оно относится. Записи без надёжного ID помечаются для сопоставления, а не автоматически объединяются по имени.

### Этап 1. Подготовить расширяемую структуру функций CM

**Действия:**

- Добавить в конфигурацию версионируемый блок функций; рабочее имя `features.collaber`.
- Определить минимальный контракт функции: идентификатор, версия настроек, включение, разрешённые события, инструменты, проверка настроек и доступность действий.
- Сохранить чтение старых конфигураций: отсутствующий блок Collaber означает «выключен».
- Встроить функцию в текущие черновик, публикацию конфигурации, паузу и выбранного исполнителя.
- Разделить общую паузу CM, выключение Collaber и режим инициатив. Учитывать их непосредственно перед действием, даже если задача уже стояла в очереди.
- Явно описать зависимость от памяти: интерфейс должен показывать, что Collaber сохраняет профили. Нельзя тайно включать сбор данных вопреки отключённой пользователем настройке памяти.
- Заложить добавление следующих функций через тот же контракт, без переноса всех нынешних подсистем CM в новую архитектуру за один релиз.

**Результат:** каркас функции и обратная совместимость настроек.

**Готовность:** без включения Collaber поведение существующих CM и Moderator не меняется; применение настройки и пауза предсказуемы.

### Этап 2. Расширить модель участников и источников

**Действия:**

- Сохранить `CommunityManagerParticipant` как общую идентичность участника внутри менеджера. Все новые записи обязаны иметь область доступа соответствующего сообщества.
- Использовать существующие claims и evidence там, где их смысл подходит. Для импортов, проектов, потребностей, предложений, согласий и знакомств добавить недостающие связанные сущности.
- Разделить устойчивые сведения и временные запросы. «Я разработчик» и «На этой неделе ищу дизайнера» имеют разные сроки актуальности.
- Поддержать несколько проектов у одного человека; указать, к какому проекту относится запрос или предложение.
- Для каждого факта хранить источник, дату исходного сообщения, дату обработки, статус подтверждения и при необходимости срок актуальности.
- Разделить уверенность извлечения и подтверждение самим человеком: высокая оценка модели не означает подтверждённого согласия.
- Описать приоритет явной правки участника над старым импортом, историю изменений и разрешение противоречий.
- Сохранить необходимые фрагменты интро и их идентификаторы независимо от краткоживущего контекста CM, в пределах настроенной политики хранения.
- Предусмотреть удаление профиля, источников, производных поисковых данных и связей; отмену ожидающих предложений. Отказ от участия должен сохраняться так, чтобы повторный импорт не включал человека снова.
- Предусмотреть состояния членства «подтверждено», «вышел», «неизвестно»; неизвестное членство исключает автоматическое приглашение до проверки.

**Результат:** схема данных и обратимо развёртываемые добавочные миграции.

**Готовность:** один человек не дублируется после смены username; данные одного сообщества не появляются в другом; устаревший запрос не считается текущим.

### Этап 3. Реализовать импорт истории

**Действия:**

- Сделать защищённую загрузку с проверкой размера, формата и принадлежности файла выбранному сообществу.
- Хранить исходный архив в закрытом хранилище с ограниченным сроком, отдельно от публичного `/uploads`.
- Показать предварительный разбор: что прочитано, что можно импортировать, какие записи требуют уточнения. Уточнять, какие оценки предварительные.
- Обрабатывать историю порциями в фоне с прогрессом, отменой, продолжением после сбоя и ограничением параллельности.
- Нормализовать сообщения и авторов, выделять вероятные интро и сообщения об изменении профиля, затем извлекать структурированные факты с источниками.
- Сохранять различие между словами автора, цитатой, пересланным интро и упоминанием другого человека.
- Обеспечить повторяемость: повторная загрузка файла и пересечение с живыми сообщениями не создают дубли. Использовать идентификаторы чата/сообщения, версию содержимого и контрольную сумму файла; не полагаться только на имя файла.
- Не отправлять ответы на старые сообщения и не запускать знакомства во время импорта. Историческая активность не должна искусственно становиться «последней активностью сегодня».
- Показать отчёт: сообщения, найденные интро, новые и обновлённые профили, пропуски, ошибки и затраты обработки.

**Результат:** контролируемый импорт с доступными для проверки карточками.

**Готовность:** повторный импорт не удваивает данные; прерванная обработка продолжается с сохранённого места; импорт не производит публикаций в чат.

### Этап 4. Подключить новые интро и обновление профилей

**Действия:**

- Подключить обработку к существующему потоку входящих сообщений, без второго независимого webhook-процесса.
- Сохранять событие быстро, а извлечение профиля выполнять фоновым заданием.
- Обрабатывать разрешённые после модерации сообщения. Сохранять сведения о версиях и учитывать редактирование, когда соответствующее событие доступно.
- Определять новое интро, дополнение к проекту, новый запрос, закрытие запроса и отказ от участия.
- Для каждого принятого изменения обновлять профиль и поисковое представление; запускать оценку только затронутых возможностей.
- Учитывать опоздавшие события: старое сообщение не заменяет более свежую явную правку.
- Раздельно обрабатывать «не упоминать», «не предлагать» и удаление. Явное действие участника немедленно блокирует несовместимые ожидающие отправки.
- Описать ограничения наблюдения: обещать обработку полученных ботом событий, а не полный контроль над всеми удалениями и изменениями Telegram.

**Результат:** база обновляется по мере жизни сообщества.

**Готовность:** новое интро создаёт или дополняет нужный профиль; повтор события безопасен; обычная реплика или чужая цитата не становится биографией автора.

### Этап 5. Сделать механизм подбора

**Действия:**

- Переводить запрос в понятные параметры: задача, нужная помощь, что автор предлагает, проект, обязательные ограничения.
- Сначала применять строгие ограничения: сообщество, видимость, отказ от участия, членство по правилам сценария, актуальность и запрет повторного нежелательного знакомства.
- Искать по всей доступной базе сообщества, используя индексы и ограниченный набор кандидатов для дальнейшей оценки. Ограничение размера контекста модели не должно ограничивать поиск первыми участниками базы.
- Оценивать соответствие запросу, дополняющие возможности, общую тему или аудиторию, формат сотрудничества и свежесть данных.
- Различать обмен и односторонний запрос: поиск специалиста не требует искусственно придумывать взаимный обмен, а кросс-промо требует проверять пользу для обеих сторон.
- Использовать AI для разбора запроса и объяснения уже найденных вариантов. Допуск к выдаче, идентификаторы людей и разрешённые действия проверяет код.
- Проверять каждое объяснение по фактам кандидата и источникам. Модель не может придумать аудиторию, оборот, готовность сотрудничать или несуществующий контакт.
- Сохранять причины включения и исключения кандидатов для диагностики. Пользователю показывать простые объяснения, без псевдоточных процентов совместимости.
- Избегать постоянного показа одних популярных участников. Учитывать историю показов и обратную связь при сохранении соответствия задаче.
- Начать с PostgreSQL и существующей инфраструктуры. Семантический индекс или embeddings добавлять, если контрольные задачи выявят недостаток поиска и измерения оправдают затраты.

**Результат:** подбор до трёх обоснованных кандидатов либо объяснимый пустой результат.

**Готовность:** результат соответствует задаче, содержит проверяемые основания, не включает самого автора, исключённых или недоступных участников.

### Этап 6. Встроить поиск в разговор с CM

**Действия:**

- Добавить инструмент поиска партнёров в `agentRuntime.ts`, доступный только при включённой опубликованной функции.
- Распознавать запрос через обращение к текущему боту, reply и поддерживаемую команду; не привязывать логику исключительно к слову «Collaber».
- Реализовать вход «Найти партнёра» из приветствия или закреплённого сообщения в личный диалог с выбранным CM-ботом. После «Начать» восстановить сообщество и проверить доступ, затем уточнить задачу.
- Передавать инструменту проверенный контекст сообщества и пользователя со стороны сервера. Модель не выбирает произвольный чужой `communityId`.
- Ответы формировать с текущей личностью и манерой CM. Использовать общий механизм решений, доставки, лимитов и учёта затрат.
- Обеспечить один ответ на событие: обычный CM и Collaber не отвечают независимо на один вопрос.
- Предусмотреть уточнение задачи, пустой результат, устаревший профиль и ошибку подбора с понятным действием пользователя.
- Отделить публичный ответ от приватного. Публичный текст содержит только разрешённые к показу данные; закрытые заметки не передаются генератору публичного ответа.
- Проверять авторизацию кнопок и срок действия: посторонний участник не может принять знакомство за автора запроса.
- Собирать ответ из необязательной обложки, 1–3 рекомендаций и клавиатуры по разделу 5.6. Переиспользовать общую отправку форматированных сообщений с учётом лимитов и журналирования CM.

**Результат:** участник получает подбор прямо в привычном разговоре.

**Готовность:** несколько формулировок одной задачи работают, ответ имеет доказательства и общий стиль CM, отключение функции останавливает доступ к действиям.

### Этап 7. Реализовать знакомство и обратную связь

**Действия:**

- Хранить отдельно рекомендацию, интерес одной стороны, приглашение другой стороне и состоявшееся знакомство.
- Реализовать прямую кнопку «Написать [имя]» для разрешённого публичного контакта, с необязательным черновиком первого сообщения. Отправляет текст сам участник; переход не подтверждает знакомство.
- Для знакомства через CM ввести состояния: предложено → первая сторона согласилась → ожидается ответ второй → обе стороны согласились → познакомлены → результат. Отдельно: отказ, истекло, отменено. Прямое самостоятельное обращение не переводить по этим состояниям автоматически.
- Кнопка «Помочь познакомиться» не означает автоматического согласия второго человека. Предусмотреть доставку приглашения только разрешённым способом.
- Если личный диалог с ботом недоступен, предложить пользователю открыть его. Публичное приглашение допускается только настройками и предпочтениями участников.
- Для перехода из общего бота в личный сценарий сохранять контекст сообщества в ограниченном по времени токене и повторно проверять пользователя и доступ.
- После взаимного согласия сформировать короткое знакомство с конкретной темой; не создавать группы и не раскрывать дополнительные контакты без соответствующего действия людей.
- После отказа остановить повторные попытки по этой возможности. Отказ от одного варианта не должен автоматически превращаться в пожизненную блокировку человека.
- Добавить необязательный отзыв: полезно / не подходит / уже знакомы / начали общение. Более поздний вопрос о результате — только в разрешённом канале и с ограниченной частотой.

**Результат:** понятный путь от рекомендации до знакомства и наблюдаемого результата.

**Готовность:** нельзя записать взаимное знакомство после согласия только одного человека; повторное нажатие кнопки не создаёт повторную отправку.

### Этап 8. Добавить инициативу и периодические предложения

**Действия:**

- Ввести три независимых режима: ответы по запросу; предложения после нового интро/потребности; периодическая проверка возможностей.
- Для новых профилей искать соответствующие открытые запросы; для нового запроса искать подходящие предложения. Не пересчитывать все возможные пары после каждого сообщения.
- Передавать найденную возможность в общий директор CM. Он учитывает текущий разговор, другие активности, общую паузу, тихие часы и лимиты.
- Разделить создание черновика и отправку. В пилоте инициативы сначала доступны владельцу в «Предложениях» и журнале.
- Задать ограничения числа инициатив, повторов по паре и нагрузки на человека. Предлагаемый консервативный старт после пилота: не более одной публичной инициативы в сутки на сообщество, с возможностью уменьшить лимит до нуля.
- Периодическая проверка не обязывает публиковать подборку. Если качественных новых вариантов нет, бот молчит.
- Повторно проверить актуальность, участие, доступ, режим и квоты непосредственно перед отправкой. При длительном ожидании пересобрать устаревший черновик.
- При неопределённом исходе Telegram-отправки не повторять её вслепую. Использовать существующий учёт доставки и отдельное состояние для разбирательства.

**Результат:** инициативный CM, который предлагает конкретную полезную возможность в подходящий момент.

**Готовность:** нет обязательных сообщений ради расписания, спама после массового импорта и обхода общей паузы через очередь.

### Этап 9. Завершить интерфейс владельца и участника

- Добавить настройку входа «Найти партнёра» через существующее приветствие или отдельное сообщение для закрепления; не заменять текущие кнопки автоматически и учитывать ограничение редактора приветствий.
- Показывать отдельные состояния «Выключен», «Черновик настроек», «Работает по запросу», «Инициативы требуют проверки», «На паузе».

- Обновить справку и вводные тексты «Участников и связей», чтобы они правильно описывали импорт, сохранение фактов и источников.

**Результат:** функция полностью управляется из существующего интерфейса без технических команд.

**Готовность:** владелец может самостоятельно загрузить данные, исправить профиль, проверить предложение, изменить режим и поставить функцию на паузу.

## 7. Технические границы и распределение изменений

Предлагаемые новые имена файлов и сущностей уточняются на этапе схемы; они не означают, что уже существуют.

| Область | Существующие точки | Предлагаемые дополнения |
| --- | --- | --- |
| Схема | `server/prisma/schema.prisma`, `server/prisma/migrations/` | Импорты, сведения о проектах/потребностях/предложениях, предпочтения, рекомендации и знакомства |
| Конфигурация | `server/src/communityManager/config.ts` | Версионирование `features.collaber`, значения по умолчанию, валидация |
| Общая память | `participantMemory.ts`, `conversationIntelligence.ts` | Доказательные сведения, правила обновления, отсутствие побочных эффектов исторического импорта |
| Логика функции | `server/src/communityManager/` | Подкаталог `collaber/`: импорт, извлечение, подбор, правила участия и знакомства |
| Агент | `agentRuntime.ts`, `conversationCoordinator.ts` | Инструмент поиска, проверка контекста и источников, единое решение |
| События | `engine.ts`, `activityDirector.ts`, `activityScheduler.ts` | Фоновые обновления профилей и инициативы через общий путь доставки |

| Интерфейс | `src/components/community-manager/` | Вход «Функции», мастер Collaber, вкладки и расширенная карточка участника |
| Сообщения и приветствия | `src/components/moderator/ModeratorRichWelcomeEditor.tsx`, `sendWelcome()` в `server/src/routes/moderator.ts`, общая отправка `sendRichMessage` | Переиспользование загрузки и предпросмотра, обложка Collaber, динамические кнопки, вход «Найти партнёра» без смены исполнителя CM |

API владельца и действия участника проверяют разные права. Контекст определяется по проверенной Telegram-авторизации и доступу к сообществу, а не по переданному клиентом ID. Получение источника и файла импорта также требует проверки доступа.

Подробные причины работы модели доступны оператору в пределах роли; публичный ответ использует отдельное представление данных. Закрытые сведения не стоит отдавать модели с надеждой, что она просто не процитирует их.

Фоновые задания имеют ограничение попыток, задержку повторов, захват задания на время обработки и восстановление после сбоя. Запись результата, переход состояния и создание следующего задания согласуются транзакционно там, где необходимо. Внешнюю отправку нельзя считать гарантированно однократной только благодаря транзакции в БД: нужен учёт результата доставки и обработка неопределённого исхода.

Если тесты разместятся в новом `collaber/`, обновляем команду их обнаружения: текущий `test:community-manager` запускает только `src/communityManager/*.test.ts`.

## 8. Хранение, актуальность и ограничения Telegram

- При импорте не нужно превращать всю переписку в бессрочную память. Основной продуктовый результат — профили, актуальные запросы и минимальные доказательства, позволяющие проверить сведения.
- Срок хранения исходного файла, выдержек и истории знакомств задаётся явно. Временный файл после обработки удаляется по политике; значимые источники живут в защищённом хранилище профиля.
- Ссылка «Показать интро» строится из сохранённых идентификаторов, когда сообщение доступно. Если оно недоступно, показывается разрешённая выдержка с датой и пометкой об источнике, без выдуманной ссылки.
- Источник из старого архива подтверждает, что человек писал о проекте в тот момент; он не подтверждает текущую готовность к сотрудничеству.
- При выходе человека из группы, отзыве разрешения или закрытии запроса актуализируются поиск и ожидающие предложения. Неполные данные о членстве не считаются подтверждением участия.
- Бот не может произвольно начать личный диалог: пользователь должен сначала обратиться к нему. Это учитывается в сценарии знакомства и не обходится массовыми личными приглашениями. Основание: [официальное введение Telegram Bot API](https://core.telegram.org/bots#how-are-bots-different-from-humans).
- Автоматическое чтение новых интро зависит от настроек бота в группе. Проверяем их при подключении; при ограниченном доступе объясняем, какие сообщения будут доступны. Основание: [Telegram Bots FAQ](https://core.telegram.org/bots/faq#what-messages-will-my-bot-get).

## 9. Матрица приёмки

Численные ориентиры ниже предлагаются для пилота; это не уже достигнутые результаты. После анализа файла фиксируем контрольную выборку и значения до настройки алгоритма под неё.

| Проверка | Условие готовности |
| --- | --- |
| Извлечение интро | На вручную размеченной выборке не менее 50 доступных интро точность извлечённых фактов не ниже 95%; отдельно измерена доля пропущенных фактов |
| Личность | Нет ошибочных объединений разных людей; смена username не создаёт второго человека |
| Источники | Все фактические основания рекомендаций имеют сохранённый источник или явную правку участника |
| Подбор | На не менее 30 разнообразных запросах с известными подходящими кандидатами хотя бы один полезный результат в первой тройке не менее чем в 80% случаев по оценке владельца |
| Нет совпадений | Отдельная подборка запросов без кандидатов не приводит к выдуманным рекомендациям |
| Изоляция | Проверены запросы к чужому менеджеру, участнику, импорту, источнику и кнопке; утечек нет |
| Отказ и удаление | Человек исключается из новых и ожидающих действий согласно выбранному отказу; повторный импорт не отменяет отказ |
| Актуальность | Закрытые и истёкшие потребности не выдаются как действующие |
| Повторные события | Повтор импорта, webhook, задания и кнопки не дублирует записи и подтверждённые отправки |
| Пауза | После паузы новые публикации не начинаются, включая ранее поставленные в очередь |
| Нагрузка | На объёме пилотного файла импорт укладывается в измеренный ресурсный бюджет и не создаёт ухудшения очереди Moderator |
| UI | Основные сценарии пройдены на мобильной ширине, видны ошибки и фокус, данные сохраняются при сбое, стиль соответствует CM |
| Вход из приветствия | «Найти партнёра» открывает нужного CM-бота, сохраняет сообщество после «Начать», проверяет доступ и не стирает прежние кнопки приветствия |
| Сообщение с обложкой | Проверены 1–3 кандидата, длинные имена, подписи кнопок, режим без картинки и ошибка изображения; источник каждого человека открывается корректно |
| Прямой контакт | «Написать» открывает нужный доступный контакт, текст отправляет пользователь; отсутствие username обработано, переход не считается знакомством |
| Действия в группе | Чужое нажатие не изменяет подбор и согласия автора; личные запросы и закрытые данные не публикуются в группе |
| Регрессия | Сборки и затронутые проверки проекта проходят; текущие CM и Moderator сохраняют поведение |

Если в файле меньше примеров, используем все доступные и явно указываем ограничение выборки. Запросы для итоговой проверки отделяем от примеров, на которых настраивали подбор. Полезность подтверждает человек; самооценка AI не заменяет эту проверку.

Текущие команды проекта: в корне `npm run build` и `npm run test:frontend`; в `server/` — `npm run build`, `npm test`, `npm run test:security`. Они выполняются после реализации на подходящем тестовом окружении. Playwright дополняет существующий frontend smoke реальными сценариями, снимками и проверкой визуальной согласованности.

## 10. Наблюдаемость и откат

В техническом журнале нужны: стадия и ошибки импорта, глубина очереди, задержка обновления профиля, время подбора, причины пустой выдачи, количество и стоимость AI-вызовов, отказанные политикой действия, ошибки и неопределённые исходы отправки. Полные архивы, секреты и лишние личные данные в лог не записываются.

Владельцу показываем понятные показатели: профилей достаточно для подбора, требуют уточнения, запросов на поиск, предложенных и принятых знакомств, полезных откликов. Не приравниваем количество сообщений бота к успеху.

Порядок восстановления при проблеме:

1. Выключить Collaber для сообщества или остановить его инициативы; заблокировать отправку его ожидающих задач.
2. Сохранить диагностические сведения и проверить, не была ли спорная отправка фактически выполнена.
3. При необходимости вернуть предыдущую версию приложения с сохранением добавочных таблиц и данных.
4. Исправить причину и проверить проблемный сценарий на тестовых данных до возобновления.
5. Восстановление БД из резервной копии применять только как отдельное решение при повреждении данных, поскольку оно затрагивает изменения после копии.

## 11. Порядок поставки результата

| Контрольная точка | Что можно проверить |
| --- | --- |
| A — этапы 0–3 | Формат файла разобран, профили импортируются, источники видны, дубли отсутствуют |
| B — этапы 4–6 | Новые интро обновляют базу, поиск по запросу работает в тестовом режиме |
| C — этапы 7–9 | Знакомства, обратная связь, инициативы и полный интерфейс готовы к проверке |
| D — этапы 10–11 | Пройдены проверки, выполнен управляемый запуск и собраны результаты пилота |

Работу над UI ведём последовательно с готовностью контрактов данных, чтобы промежуточные результаты можно было посмотреть и проверить. Каждая поставка включает код, миграции при необходимости, результаты проверок и актуализацию соответствующей документации.

Календарную оценку уточняем после изучения файла и оценки объёма импорта. Критический путь: надёжная идентификация участников → доказательные профили → качество подбора → действия знакомства → инициативы и пилот. В первой реализации не требуется внешняя векторная база, обучение собственной модели или переработка всего Community Manager.

Итоговый отчёт реализации должен содержать выполненные пункты, снимки интерфейса, результат импорта, примеры проверенных рекомендаций, результаты тестов, ограничения фактических данных, состояние пилота и доступный порядок отката.
