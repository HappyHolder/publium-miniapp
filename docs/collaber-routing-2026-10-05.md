# Collaber: поиск по естественному запросу в группе

## Подтверждённая причина

Сообщение №457 в Test Publium Chat от 05.10.2026 распознано как обращение к CM. Агент выбрал `answer_project_query`, сослался на собственный прежний ответ, а `collaberRequestId` оставил пустым. Запроса Collaber и попытки rich-выдачи не было. Исправление контекста интро от 04.10 не решало выбор между разговором и поиском.

## Поведение после изменения

В `engine.ts` после проверки модерации и разрешённого способа обращения, перед разговорным агентом вызывается `handleGroupCollaborationQuery`. Это действует для включённого Collaber с onDemand в режиме AUTOPILOT, при обращении к боту. Ответы другому человеку и сообщения с тегом интро не перехватываются.

Отдельная классификация возвращает одно из трёх решений:

- `SEARCH`: поиск людей, специалистов, команд, проектов или сервисов под заявленную тему. «Есть проекты с проверкой человечности?» достаточно для поиска; слово «найди» не обязательно. Код создаёт запрос и вызывает существующий Collaber delivery. При совпадениях выдаются обложка, объяснение, кнопки контакта и проверенного исходного интро согласно настройкам.
- `CLARIFY`: просьба найти партнёра совсем без задачи. Бот задаёт один вопрос. Ответ того же автора через Reply на уточнение связывается с прежним запросом в течение суток.
- `NONE`: обычная беседа, объяснение технологии, приветствие, отмена поиска, запрос внешнего веб-поиска и другие несвязанные сообщения. Продолжает работать разговорный CM.

Решение кешируется по исходному событию в `CollaberTask(kind=ROUTING)`. Повторная обработка использует тот же запрос и не повторяет отправленную карточку/уточнение. Данные автора в кеше очищаются штатным `/forget`. Некорректное решение классификатора приводит к ошибке и штатному повтору, а не к скрытой подмене поиска свободным ответом. Прежний необязательный `find_collaboration_partners` удалён из инструментов разговорного агента. Чтение прежних сохранённых решений агента сохранено для совместимости.

Добавляется один короткий AI-вызов классификации нового подходящего обращения. Он использует только текст запроса, тип сообщества и, при наличии, контекст собственного уточнения. Вызов учитывается в журнале `collaber_inference`; интро и архив классификатору не нужны. Сам подбор по-прежнему использует профили.

Собственный профиль автора исключается из рекомендаций. Отсутствие кандидатов даёт понятный текст без картинки. Изменение не добавляет автоматических приглашений, не загружает архив, не меняет расписание, лимиты, настройки сообщества или схему БД. Старые обработанные сообщения не переигрываются.

## Проверки

- 76 CM-тестов, серверная сборка и security smoke прошли.
- Изолированная PostgreSQL `publium_audit_collaber_20260921`: 60 миграций без расхождений, весь сценарий прошёл с заглушками AI/Telegram. Новый тест проверяет обработчик от классификации до rich-выдачи со ссылкой и кнопкой контакта, отсутствие дубля, исключение ответа человеку, обычную беседу, продолжение уточнения и исключение собственного профиля.
- Реальная настроенная модель: 8 из 8 полностью синтетических фраз получили ожидаемый маршрут (поиск, приветствие, объяснение, уточнение, продолжение и отмена). Всего 3098 входных и 144 выходных токена. Сохранённые интро и сообщения пользователей для этой проверки не читались и не передавались; Telegram-вызовов не было.
- Frontend production build/smoke прошёл, включая авторизацию и Telegram launch fallback. Изменений интерфейса Mini App нет.

Остаётся пользовательский контроль после выкладки: с существующего аккаунта тестового разработчика/владельца мини-приложения спросить в группе `@Publium_CM_Bot Есть какие-то проекты с проверкой человечности?`. Проверить, что появляется Collaber-выдача, а кнопка интро ведёт к нужному участнику. Новые аккаунты/интро и повторные согласия не нужны. Живой подбор по сохранённым профилям в этой проверке не запускался.
